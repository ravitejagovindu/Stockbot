# Daily data update: design (stage 1, nothing built)

Owner direction (fixed): ONE working database with the same tables; the daily job appends each new session to it and is its only writer; the paper runner reads it as today. Research and backtests run on a FROZEN SNAPSHOT COPY pinned by sha256; the current content is **snapshot 1** with its existing hash, so every recorded result stays valid. Daily job at 19:30 IST. Facts behind every statement are in `INVENTORY.md` (same folder). This file proposes; "recommended" marks a default the owner can change (section 8 lists them).

**What stops the wrong pairing (role marker, no file name tricks).** The working database has a one-row table `ingest_meta(key, value)` with `role = working` (created by the init command, section 7 stage 1). Snapshots do not have it (snapshot 1 cannot get one: it is never modified; a cut snapshot has it dropped). Two small guards:
1. `run_backtest` and every research script refuse a lake that has `ingest_meta` ("this is the working database: backtests run on a snapshot").
2. The paper entry point (`scripts/run_eod_paper.py` and the chain) refuses a lake that does NOT have `ingest_meta`, and the data job refuses any file that lacks it.
Both are one `select` on `sqlite_master`; they only add a refusal, never change a number (proof in section 7). The library function `run_eod(...)` itself is unchanged, so its fixture-lake tests keep working.

**Cutting a new snapshot later** (`daily_data.py cut-snapshot --name N`, under the job lock):
1. `PRAGMA wal_checkpoint(TRUNCATE)`; copy with the SQLite online-backup API (consistent even if a reader is open) to `snapshots\finsight_snapshot_N_<date>.db`;
2. open the COPY: drop `ingest_meta`, the insert-only triggers and the ingest bookkeeping tables, `PRAGMA journal_mode=DELETE`, `VACUUM` is NOT run (page layout stays as copied); close;
3. set the read-only attribute, compute sha256 (about 45 s), compute the prefix digest of the rows with `id <=` snapshot 1's maximum id and require it to equal snapshot 1's digest (evidence that history was not rewritten);
4. write the SNAPSHOTS.json entry (also the sha256 of the two reference files and the link table) and print it. The owner commits it.
Nothing registered changes: a registered run is pinned to the sha256 it recorded (snapshot 1); new pre-registrations name the snapshot they will run on. Snapshots are never edited, deleted or moved by the job.

Growth of the working file: about 2,700 lake rows and 2,700 staging rows a session, roughly 1 to 2 MB a day (estimated from about 230 bytes per row over the file's 14 million rows; to be measured in stage 3), about 0.4 to 0.7 GB a year. ## 2. The daily job for one date D (design 2b)
Command: `py -3 scripts/daily_data.py update [--date D]` (default: every date from the last loaded session + 1 up to today, in order; section 6). One date goes through six steps; a failure stops the chain for that date and for every later date.

**Step 0, preflight.** Take the writer lock (`working\.lock`, created exclusively, holds pid and time; a lock older than 6 hours whose pid is dead is broken and logged). Open the working file read-write (`timeout=60`), require `ingest_meta.role = working`, `journal_mode=WAL`, the insert-only triggers present, and the stored prefix digest equal to a fresh one (section 3). Take the backup (once per run, not per date).

**Step 1, candidates.** L = the last Nifty date in the lake. Dates L+1 to today (IST) are tried in order. Saturdays and Sundays are tried too (special sessions such as Diwali Muhurat exist: `data/reference/special_sessions.csv`); a weekend file that passes every check is NOT promoted automatically (it stops with exit code 4, "special session found, confirm with `--allow-special D`"), because it adds a session to the calendar. Weekday dates need no confirmation.

**Step 2, fetch** (existing, proven code reused by import: `ingest_raw_bhavcopy_range.fetch_day`, `parse_bhavcopy`, `candidate_urls`; the module's `main` is NOT used). Order: UDiFF, full `sec_bhavdata_full`, legacy (as `candidate_urls`). Three attempts per URL with 2 s, 4 s, 6 s back-off, 30 s timeout. The file's own date must equal D (else the date is "not a session or not yet published"). EQ rows only. The raw bytes' sha256 and the URL go to `bhavcopy_fetch_log` (one new column `content_sha256`, added by the job's own migration on the working file) and `ingest_log`. Index rows: the NSE index file `https://archives.nseindia.com/content/indices/ind_close_all_DDMMYYYY.csv` (`Index Name` "Nifty 50" and "India VIX"; its `Index Date` must equal D); only if that file is missing after the retries, Yahoo `^NSEI` / `^INDIAVIX` for D, labelled `yahoo:<ticker>` in `source` (as in `f2_index_gap_fill_yahoo`).

**Step 3, stage.** One transaction: `DELETE` of D in `market_data_lake_staging`, insert of the parsed rows (`symbol, trade_date, OHLC, volume, prev_close, isin, series, source`), `bhavcopy_fetch_log` row `OK`. Staging is a scratch table for D; it also keeps ISIN and previous close, which the rename watch (section 4) and the fund list need, so staging is appended every day exactly as the lake is.

**Step 4, validate** (all read-only; thresholds are recommended defaults, calibrated in stage 2 against the last 250 lake sessions before they are frozen; each check writes pass, warn or fail with numbers to `ingest_log`). A fail stops the date, writes nothing to the lake and ends the run with exit code 2.
| # | check | warn | fail |
|---|---|---|---|
| V1 | declared date equals D; EQ rows parsed; required columns present | - | any |
| V2 | EQ row count against the previous session | change over 3% | change over 10%, or fewer than 1,500 rows |
| V3 | symbols present on the previous session and missing on D (and new ones) | more than 1% missing | more than 5% missing; a symbol held in the paper state missing is always reported by name |
| V4 | prices: every open, high, low, close greater than 0 and finite; low <= open, close <= high | any row | more than 0.2% of rows |
| V5 | close against the file's own previous close: share of rows moving more than 20% | over 0.5% | over 2% |
| V6 | **continuity**: the file's previous close against the lake's close of the last loaded session, per symbol (excluding symbols with a corporate action on D) | under 99.5% equal | under 97% equal (this catches a wrong, stale or revised previous load) |
| V7 | volume: not negative; share of rows with volume 0; total traded value against the 20-session median | over 1% zero-volume, value outside 0.3x to 3x | negative volume; value outside 0.1x to 10x |
| V8 | duplicates: one row per symbol in the file; D is not already in the lake; D is after the last loaded date | - | any |
| V9 | NIFTY50_INDEX and INDIA_VIX rows for D present; Nifty within 8% of the last close; VIX between 5 and 100; high >= low | Yahoo used | either row missing, or out of range |
| V10 | weekend date: see step 1; weekday with no file: see below | - | - |
No file for D (weekday): not an error. The job records `pending`, retries as below, and after the give-up time leaves D `pending`. A weekday is confirmed as a holiday only later, by V6 on the next loaded session (its previous close equals the close before D, so no session lay between); until then the status file says `pending (holiday or not yet published)`.

**Step 5, promote** (one transaction, `BEGIN IMMEDIATE`; section 3 for the checks around it):
```
INSERT INTO market_data_lake (symbol, trade_date, open_raw, high_raw, low_raw, close_raw, volume_raw, exchange, created_at, source, loaded_at)
SELECT symbol, trade_date, open_raw, high_raw, low_raw, close_raw, volume_raw, 'NSE', :now, 'nse_bhavcopy_raw', :now
FROM market_data_lake_staging WHERE trade_date = :D AND series = 'EQ'          -- the F2 statement (f2_swap.py:129)
```
plus the two index rows (volume 0, `source` the URL or `yahoo:<ticker>`). Symbols are stored as traded (`source_symbol` NULL); a rename is handled by a symbol link, not by relabelling rows (section 4). Then in the same transaction the row counts are asserted: inserted EQ rows = staged EQ rows, index rows = 2, and `ingest_log` gets `PROMOTED`. COMMIT. After the commit: the post-run checks of section 3, then the reference upkeep of section 4 (rename watch, fund list), then the next date.

**Step 6, release.** Unlock, `PRAGMA wal_checkpoint(TRUNCATE)` (retried 3 times; a long-open reader only delays it), write `daily_status.json`.

**The file is not published at 19:30.** The job starts at 19:30; for the newest date it retries every 20 minutes (19:30, 19:50, ... ) until **23:30 IST** (the give-up time), 13 attempts. Give-up is exit code 3 ("pending, will be caught up"), not a failure. The next start (section 6) tries again from L+1. If a weekday stays `pending` for 3 sessions in a row the status file says `STALE: 3 weekdays without data (outage or holidays)` and the exit code is 2 from then on, so that an NSE URL change cannot pass unnoticed. When the first week's logs exist the first-success time of each day is read from them and the schedule is tuned (the publication time of NSE's files is not recorded anywhere in the repo; I did not measure it).

**A late or revised file.** If a date is already loaded and the file now differs (the job refetches the last loaded session once per run and compares `content_sha256`), nothing is changed: it writes `REVISION_DETECTED` to `ingest_log`, sets exit code 4 and names the date. Handling is the correction path of section 4.

## 3. Safeguards (design 2c)

**Insert-only, enforced twice.**
1. **In code**: the promote function refuses any date not strictly after the last loaded date, any date already present, and any statement other than the one INSERT above on `market_data_lake`; it contains no `UPDATE`, `DELETE` or `REPLACE` of lake rows.
2. **In the database**: triggers on the working file only (not in snapshot 1):
`CREATE TRIGGER mdl_no_update BEFORE UPDATE ON market_data_lake WHEN (SELECT allow FROM ingest_control) = 0 BEGIN SELECT RAISE(ABORT,'market_data_lake is insert-only'); END;` and the same for `DELETE`; `ingest_control(allow)` is 0 and is set to 1 only inside the correction command of section 4, in the same transaction, and set back to 0 before COMMIT. The same pair protects `corporate_actions_log` against accidental deletes (updates go through the correction command). Any other tool that tries to modify a lake row fails with the abort message.

**Post-run check that every row up to the previous last date is unchanged.** Method: a SHA-256 over `(id, coalesce(source_symbol, symbol), trade_date, open_raw, high_raw, low_raw, close_raw, volume_raw)` for all rows with `id <= max_id_before`, in id order (the method of `f2_swap.checksum`, extended with `id` so a re-ordered or re-numbered row also shows). The digest and the row count are stored in `ingest_log` after every successful run; the next run recomputes it BEFORE it does anything (catches changes made between runs) and again AFTER the promote (catches changes made during it), and compares both with the stored one. **Run time**: measured today on the 5,634,334 rows with the columns above (without `id`): 23 s on this machine; with growth of 2,700 rows a day it stays under 30 s for years; two computations a run = about 1 minute. A cheap cross-check (`count`, `sum(id)`, `sum(close_raw)`, `sum(volume_raw)`: 1.7 s) also runs. A mismatch stops everything with exit code 2 and the message names the first differing id range (bisection by id ranges, a second pass of about 25 s). A weekly `PRAGMA quick_check` (minutes on 3.4 GB; to be timed in stage 3) catches page damage.

**Backup before each run, how many kept.** One copy, taken with the SQLite online-backup API (consistent while a reader is open) at the start of every run that has something to load: `finsight_working_pre_<last session>.db` plus its sha256 (and `PRAGMA quick_check` of the copy is NOT run daily). A new backup replaces the previous one only after the new one has been written and its sha256 verified, so there is always exactly one verified pre-run copy; it stays after a successful run until the next run replaces it. This is the owner's standing "one local backup is enough" policy. Time: about 15 to 40 s for 3.4 GB (a cached read of the file took 2 s; a disk write was not measured). Snapshots (section 1) are separate and permanent.

**Behaviour if a reader has the file open while the job writes.** The working file is in WAL mode: readers see the state before the commit until they finish their read transaction; the writer is not blocked by readers; a writer blocks other writers only (`timeout=60`). The only thing a long reader can do is delay the final checkpoint (retried, then skipped with a warning: the next run does it). Nothing else is expected to read the working file at 19:30 except the paper step, which runs after the data step in the same chain. Ad hoc reading of the working file is read-only (`open_lake` is `mode=ro` and `query_only`).

**Idempotent re-run of a failed or partial day.** The lake changes only in the single promote transaction, so a day is either fully in or not at all. Re-running: staging for D is replaced (delete, insert), `ingest_log` shows the step reached; a date whose `PROMOTED` row exists is skipped; a crash between COMMIT and the log write is detected because D is in the lake and not in `ingest_log` (the job then runs the post-run checks and writes the missing line). The ASM/GSM snapshot is `INSERT OR IGNORE` per day already (`snapshot_asm_gsm.py:125`). The paper run is idempotent per date (`adapter.py:59`).

## 4. Corrections after the fact (design 2d)
The rule is that `market_data_lake` rows are never changed by the daily job; every other kind of change below is logged in a new table `ingest_change_log(at, kind, table_name, key, before_json, after_json, reason, run_id)` written in the same transaction as the change.

- **Corporate actions announced or corrected after a session was loaded.** The adjusted series is not stored (`MarketDataLake` docstring, `models.py:19`): the as-of view recomputes adjustments from `corporate_actions_log` on every read (`asof.py:176` to `:203`), so a new row is used by the next paper run with no change to prices. New events: `INSERT OR IGNORE` on `UNIQUE(symbol, ex_date, action_type)`, evidence tier and source as in F2 (`f2_load_corporate_actions.py`), keyed to the lake symbol holding the pre-ex prices (`lake_symbols.py:8`), feed symbol in `notes`. A corrected event (wrong ratio, wrong date) goes through `daily_data.py correct-ca` which opens the gate (`ingest_control.allow = 1`) for that table only, writes before and after to `ingest_change_log`, closes the gate, and prints the affected symbols. A position already open when an action with an earlier ex-date is added is handled by the engine's own rule (`engine/corporate.py:31` `due_actions`: actions with entry < ex-date <= the processed date not yet in the position's `ca_done` are applied when the next session is stepped); the session decided before the action was known is not replayed (the journal is append-only), and the job lists open positions whose symbol received a new action with an ex-date in the last 5 sessions in `daily_status.json` for the owner. How the late application behaves with the paper state is to be proven by a fixture test in stage 6 before paper starts.
- **Refreshing the log.** Weekly (Sunday) the NSE history for the symbols of the paper state and the top 300 by ADTV is fetched per symbol (`nse_corporate_actions_history.py`, 0.6 s apart, about 3 minutes); every other symbol monthly (about 27 minutes for the 2,700 symbols of the lake); `--load` is `INSERT OR IGNORE`. Whether the NSE API also answers a date-range query without a symbol is not verified (no downloads in stage 1); stage 6 tests it once.
- **Symbol renames.** `data/reference/symbol_links.csv` is derived (`scripts/build_symbol_links.py`) from `isin_symbol_map.csv` (derived by `f2_build_isin_symbol_map.py` from staging ISINs plus the NSE actions dump) and the lake. Keeping both current needs the ISINs, which only staging has: that is the second reason staging is appended daily. Daily **rename watch** after each promote: an ISIN that traded under symbol A on the previous session and under symbol B on D with A absent; the pair is linked automatically only if the strict build rule holds (same ISIN, new first bar 1 to 5 sessions after the old last bar, no overlap, price ratio 0.80 to 1.25 after any split/bonus between them, unambiguous; `build_symbol_links.build`, run on the new boundary only), appended (never edited) to the WORKING copy of `symbol_links.csv`, logged in `ingest_change_log`, and named in the status file. Any other change of symbol for an ISIN (a gap, an overlap, a price step) is reported, not linked. The link is in force before the paper step of the same chain, so a held stock that is renamed keeps its position and its history (without it the 20-session stale exit would close it). The repo's `symbol_links.csv` and `isin_symbol_map.csv` are regenerated by hand monthly from the working file and committed; they stay the files pinned by snapshot 1 and its research runs (the manifest already records the links file's sha256, `manifest.py:66`).
- **ETFs and funds.** `fund_etf_symbols.csv` (ISIN starting INF) is rebuilt daily from the new staging rows into the working copy (append of new INF symbols only), because an ETF absent from the list is eligible for the strategy if its ADTV passes.
- **A revised Bhavcopy for a loaded date.** Detected as in section 2 and stopped. Correction (`daily_data.py correct-prices --date D`, explicit): copies the old rows of D to a new archive table `market_data_lake_revisions` (as `market_data_lake_yahoo_archive` was used in F2), updates the rows with the gate open, logs before and after per symbol, then prints that decisions of the paper runner made on D or later were based on the earlier values; the paper state's journal is not rewritten (a flagged review, see open questions). Snapshots cut before the correction keep the old values by construction.
- **What is logged**: `bhavcopy_fetch_log` (every fetch with its URL and content hash), `ingest_log` (per date and step with the numbers of each validation), `ingest_change_log` (every change that is not an insert of new session rows), the daily text log, and `daily_status.json`.

## 6. Scheduling on Windows Task Scheduler (design 2f)
Facts: a laptop; time zone India Standard Time; the sleep state is "Standby (S0 Low Power Idle) **Network Disconnected**", so a sleeping laptop has no network and a wake-to-run trigger would start a job that cannot download. The design therefore does not depend on waking: it catches up.

**One task, one chain**, not three tasks (Task Scheduler cannot make a task run only after another succeeded): `StockBot Daily`, action `py -3 scripts/daily_chain.py` from the production checkout (open question 1), environment as in section 1:
1. **data update**: `daily_data.py update` for every date from the last loaded session + 1 to today, in order (section 2). Exit code 0 only if the lake's last session equals the newest published session at the time.
2. **ASM/GSM snapshot** (`snapshot_asm_gsm.py`, today's lists, `INSERT OR IGNORE`): always runs, also if step 1 failed (it is today's state and cannot be fetched later), in the working database.
3. **paper run** (`scripts/run_eod_paper.py`): runs ONLY if step 1 ended with exit 0 and the lake's last session is at least the last session the paper state has not processed; it processes every unseen session in order, one `decide` per session (`adapter.py:71`).
4. **health check** (`stockbot/live/health_check.py`, read-only) and the status file.

**Triggers** (all start the same chain): daily 19:30; daily 06:30 (catch-up while the laptop is on); at log on; on workstation unlock. Settings: run as soon as possible after a missed start; start only if a network connection is available; do NOT wake the computer; do not start a second instance (`IgnoreNew`); stop after 6 hours; allowed on battery. Because every start processes everything missing from the last loaded session on, a laptop that was off for days is caught up in order at the next start, each session passing the same checks (V6 chains the days, so a missing day in the middle is detected, not skipped).

**What catch-up means for the paper run.** The adapter decides one session at a time. For a session missed by the laptop the tickets are produced late (their entry price assumption is the next open of a day that has already passed): the file for a session older than the latest is marked `late: true` in its name (stage 7) and the status file lists it; the operator reports them as not taken or as filled (`engine/reports.py`). Default: process, mark, list.

**Exit codes of the chain** (also the task's "Last Run Result"): 0 all done; 1 unexpected error; 2 data check failed (a date not promoted, or a stored-rows check failed: needs the owner); 3 file not published by 23:30 (pending: not an error, caught up at the next start); 4 needs a human decision (special session found, revised file); 5 ASM/GSM snapshot failed (data and paper ran); 6 paper run failed. The chain exits with the highest of them (3 counts as 0.5: it never hides a 2 or 4).
