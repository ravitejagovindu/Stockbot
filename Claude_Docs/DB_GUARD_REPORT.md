### Requirements a to e
* **a. WAL and header bytes.** Tests prove that opening through `open_lake`, through the memory view (`MemoryAsOfView`) and through the ORM engine leaves the main file byte-identical (sha256) and its journal-mode header bytes unchanged, for both a rollback-journal and a WAL file. **Defect found and fixed:** `stockbot/data/db/connection.py` ran `PRAGMA journal_mode=WAL` on every ORM connect, which rewrites the header of any file in another mode; it now sets WAL only when the file has no pages yet (a file it creates). The staging writer `ingest_raw_bhavcopy_range.py` had the same line and got the same guard. **Side files:** the `-shm` file is rewritten by every read-only connection to a WAL database, so it is deliberately NOT part of any check; the `-wal` file is checked by size (a non-empty one means the main file alone is not the whole database; the real file's `-wal` is 0 bytes before and after). Tests assert `-wal` is absent or empty after each read path.
* **b. Writers.** Changed: `corporate_actions_ingestor._bulk_upsert`, `nse_corporate_actions_history.load`, `securities_ingestor` (both `INSERT OR REPLACE` sites), `shares_outstanding_ingestor._upsert`, `bhavcopy_ingestor` (new `store_day`). Each adds new rows, skips identical ones and reports different ones without applying them (a change is `guard correct`). Each has a test that a sealed (or insert-only) row cannot be changed through it and that a new row can be added. The OHLCV and index/VIX writers needed no change (their upserts are refused on sealed dates by the triggers); both have tests through the writers' own methods. **Daily lake writer:** `store_day` refuses a sealed date BEFORE deleting anything and does delete-and-insert in one transaction (a failed reload leaves the day as it was; tested). **What stays unsafe on unsealed days:** the day's rows are still replaced on reload; an unparsable price is still turned into 0.0 (zero-fill); and a half-loaded day is only frozen by a later `seal`. The old behaviour is impossible on a sealed date.
* **c. `guard uninstall`.** Refuses without `--yes-remove-guard` (tested; also run on a real-size copy: 128 triggers and 6 tables removed, per-table proof identical to the original, integrity ok). Documented in GUARD.md.
* **d.** Steps 1 to 5 were fully green on the scratch copy and the backup check passed (sha256 equal, `integrity_check` ok), so the migration went ahead without a stop.
* **e.** After the migration: per-table proof identical for all 25 tables (plus `sqlite_sequence`), `integrity_check` ok, new hash printed, full G2 on the real file (above), and the fixture end-to-end backtest with and without the guard is byte-identical (`test_an_end_to_end_backtest_is_byte_identical_with_and_without_the_guard`: decisions, trades, equity curve, final state and the manifest apart from `db_check` and the two files' own size/mtime; it also runs inside the full G2 on the real file).

## 6. Deviations and choices to review
1. **Writers do not seal their own day** (my Part 1 default D12, not among your decisions D1 to D8). Reason: the equity writer and the index/VIX writer both load `market_data_lake` for the same date, so an early seal would block the second writer. `seal TABLE DATE` is explicit; the daily job should seal once every lake writer has finished.
2. **`shares_outstanding_pit`** is in the registry (DATED on `effective_date`) although it is not in the file: `scripts/provenance/f2b_build_pit_shares.py` would create it, and R5 forbids an unregistered table.
3. **Identical re-insert of an insert-only row is ignored, a different one is refused** (also under `INSERT OR IGNORE`): earlier code silently kept the old row on `INSERT OR IGNORE` of a changed fact; now that is an error, loud on purpose.
4. **Signal-count scripts keep their full file hash** (they already hashed); D3 asked for the lighter check on short steps, which is a subset of what they do, so I left them stricter.
5. `trade_analytics_log` keeps its two native triggers, which refuse UPDATE and DELETE even inside a correction window (stricter than the guard); correcting that table would first need those triggers dropped by hand.

## 8. What the guard cannot prevent
`DROP TRIGGER`, `DROP TABLE`, `ALTER TABLE` and `PRAGMA writable_schema` (SQLite has no DDL triggers): the audit finds the result afterwards (test: a row changed after the triggers were dropped is reported, with the missing triggers). Replacing or editing the file outside SQLite: a run's before/after file hash catches it for that run. Opening a window with a plain `UPDATE _guard_window`: not prevented, but it leaves a counter change and a log entry. Rows after the sealed date are free by design (including everything on an unsealed day). A new database created by `to_sql` into a fresh file, or `CREATE TABLE AS`, is not guarded (the manifest says `installed: false`). The separate live state database `state/live_state.db` is outside the guard (D5). Late-arriving insert-only facts (a corporate action with an old ex_date) are allowed by design; they show up as a digest difference in the next run's manifest.
